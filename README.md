# ПочтаТех — Квартальное планирование и звёздная карта компетенций

Сервис автоматизирует квартальное PI-планирование для нескольких инженерных команд и одновременно показывает распределение компетенций и риски, связанные с уникальными носителями навыков.

Проект состоит из двух обязательных частей:

- планировщик, который распределяет задачи по 6 двухнедельным спринтам с учётом Story Points, человеко-часов, зависимостей и доступности специалистов;
- звёздная карта, которая считает Bus Factor по компетенциям и показывает, какие навыки держатся на одном человеке.

## Требования

- Windows 10 или 11
- **Python 3.10, 3.11, 3.12 или 3.13** — рекомендуется 3.12 или 3.13
- Python 3.14 и выше не поддерживается: часть библиотек (numpy, pandas) не имеет готовых колёс под эти версии, установка может упасть при сборке из исходников

При установке Python обязательно отметить галочку **«Add Python to PATH»**.

Проверить установленную версию:

```powershell
python --version
```

Если команда не найдена или версия ниже 3.10 — переустановить Python с [python.org](https://www.python.org/downloads/).

## Запуск

### Способ 1. Через `.bat` (рекомендуется)

1. Скопировать папку проекта на локальный диск (не запускать из сетевой папки или из `Program Files`).
2. Положить файл `dataset.xlsx` в одну из папок: `data/`, корень проекта или `src/data/`.
3. Запустить `Planirovanie.bat` двойным кликом.

Скрипт сам проверит Python, создаст виртуальное окружение `.venv`, поставит зависимости из `requirements.txt` и откроет приложение в браузере. Первый запуск занимает 1–3 минуты, повторные — несколько секунд.

### Способ 2. Вручную из PowerShell (с venv)

Открыть PowerShell и выполнить:

```powershell
cd C:\путь\к\проекту
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run src\app.py
```

`cd` — переход в папку проекта. `venv` создаётся один раз, при повторных запусках его создавать не нужно.

Запустить приложение (после того как venv уже создан):

```powershell
cd C:\путь\к\проекту
.\.venv\Scripts\python.exe -m streamlit run src\app.py
```

### Способ 3. Вручную без venv, глобальным Python

Если не хотите возиться с виртуальным окружением и готовы поставить пакеты в системный Python:

```powershell
cd C:\путь\к\проекту
python -m pip install -r requirements.txt
python -m streamlit run src\app.py
```

Здесь `python` — это глобальный Python из PATH, версии 3.10–3.13. Все пакеты установятся в него. Такой способ проще, но менее изолирован: если позже обновите или сломаете какой-то пакет в глобальном Python, это затронет и другие проекты.

### Как остановить

`Ctrl+C` в окне терминала (или в окне `.bat`). Окно закроется, приложение остановится.

## Входные данные

Проект работает с одним Excel-файлом, который содержит 5 секций подряд на одном листе.

**Tasks** — список задач. Используются поля: `task_id`, `parent_id`, `summary`, `team_id`, `status`, `rung`, `estimation_sp`, `estimated_hh`, `Номер инициативы`, плановые и фактические даты.

**Estimates** — матрица трудозатрат. Строки — роли, столбцы — `task_id`, значения — человеко-часы.

**Task_dependencies** — направленный граф зависимостей: `blocking_task_id`, `blocked_task_id`, `dependency_type`.

**Engineers_profiles** — инженеры: `engineer_id`, `team_id`, `role`, `grade`, `skills_declared`, `capacity_rate`.

**Team_history** — история производительности: `snapshot_date`, `team_id`, `velocity_achieved`, `planned_sp`.

Парсер читает файл как единую сетку без заголовков и вырезает секции по маркерам шапок. Имена колонок в шапке не используются, только позиции — это устойчиво к сдвигам.

## Алгоритм планирования

### Ёмкость команды в Story Points

Номинальная ёмкость команды на спринт рассчитывается по истории:

```
доступная ёмкость = средний velocity_achieved × 0.8
```

Коэффициент 0.8 — Focus Factor, учитывает техдолг, баги и созвоны. Значения velocity берутся из `Team_history`, некорректные и отрицательные строки игнорируются. Если для команды задан ручной override SP capacity через интерфейс, он используется вместо расчёта из истории.

### Фонд человеко-часов по ролям

```
hours_per_sprint = capacity_rate × 80
```

Ставка 1.0 даёт 80 часов за 2-недельный спринт, ставка 0.5 — 40 часов. Часы суммируются по связке «команда + роль» отдельно для каждого спринта.

Больничные и отпуска учитываются поспринтово: если период отсутствия инженера пересекается со спринтом, инженер исключается только из этого спринта. Если даты отсутствия не заданы, инженер исключается из всего квартала. Уволенные исключаются полностью.

### Приоритет задач

Задачи сортируются лексикографически:

```
(active, -rung, init_size, task_id)
```

- `active` — 0 для задач в статусе InProgress, 1 для остальных. Начатые задачи получают приоритет.
- `-rung` — больший rung раньше.
- `init_size` — суммарный SP инициативы, меньшие инициативы раньше.
- `task_id` — стабильный tie-breaker.

Порядок внутри графа зависимостей сохраняется: потомок не может быть раньше предшественника.

### Зависимости

Между блокирующей и блокируемой задачей выдерживается минимум один спринт зазора. Реализовано условием `sprint_when_done[predecessor] < current_sprint`. Циклы зависимостей обнаруживаются через NetworkX, задачи цикла исключаются из автоматического планирования.

### Двухпроходное распределение

Для каждого спринта создаются свежие пулы SP и ЧЧ.

**Проход 1.** Каждая команда закрывает задачи своими силами. Если часов по всем ролям хватает, задача планируется в этом спринте. Если SP команды меньше требуемого (и SP ещё не были закоммичены), задача переносится на следующий спринт.

**Проход 2.** Для задач, которым не хватило часов, ищутся доноры. Донором может быть другая команда, у которой после первого прохода остались свободные часы нужной роли. Дополнительно проверяется, что в команде-доноре есть хотя бы один инженер с ключевым навыком для этой роли. Часы переводятся жадно, по убыванию доступного объёма. Пользователь может запретить конкретную связку «команда + роль».

### Сплиттинг

Если задачу нельзя выполнить целиком в одном спринте, но часть часов доступна, выполняется доступный объём, остаток переносится в следующий спринт. Story Points резервируются один раз, при первом включении задачи. При повторном включении в следующий спринт SP не списываются.

### Story Points и человеко-часы

SP и ЧЧ — независимые величины.

SP отражают сложность задачи и являются обязательством команды перед заказчиком. Списание SP происходит один раз, при первом включении задачи в план. Если задача растягивается на несколько спринтов, SP не пересчитываются.

ЧЧ отражают конкретную загрузку специалистов по ролям. Именно ЧЧ расходуются из поспринтовых пулов, и именно они определяют, влезает задача в спринт или нет.

Связь между SP и ЧЧ в алгоритме отсутствует: это две отдельные шкалы, которые используются параллельно.

## Пересчёт по факту

Раз в две недели пользователь отмечает задачи, реально завершённые в спринте. По умолчанию в интерфейсе отмечены все задачи, запланированные к завершению — снимаются галочки с тех, что фактически не закрылись.

После внесения факта планировщик:

- принимает отмеченные задачи как завершённые и фиксирует списание часов по факту;
- для незакрытых задач из baseline показывает статус «Не выполнена (Факт)»;
- для сплитованных задач переносит остаток часов без повторного списания SP;
- пересчитывает оставшуюся часть квартала.

Отклонения вызывают алерты:

- красный — задача не завершена за 6 спринтов, инициатива под угрозой;
- жёлтый — задержка задачи реально блокировала потомков по графу зависимостей;
- оранжевый — ресурсный дефицит по роли в конкретном спринте, либо перерасход факта относительно фонда.

## Звёздная карта и Bus Factor

Для каждого навыка считается Bus Factor — сколько разных инженеров им владеют. Навык с Bus Factor = 1 считается критичным.

Для критичных навыков подбираются кандидаты на дообучение по принципу TF-IDF: вес навыка обратно пропорционален числу его носителей, поэтому редкие навыки дают больший вес при подборе кандидата. Если кандидат сам является единственным носителем какого-либо навыка, его оценка умножается на 0.5, чтобы не создавать новое узкое место.

Дополнительно считается Bus Factor в разрезе отдельных команд. Навык может быть не критичным для компании в целом, но критичным для конкретной команды — тогда именно эта команда остановится при уходе носителя.

В интерфейсе отображаются:

- KPI по доле критичных навыков;
- тепловая карта «навык × команда» — сколько инженеров в каждой команде владеют каждым навыком;
- полная таблица Bus Factor по компании и по командам;
- связка критичных навыков с конкретными задачами квартала.

Уволенные инженеры исключаются из расчёта Bus Factor сразу после перевода в соответствующий статус.

## Показатели эффективности

**PI Predictability Measure** — доля инициатив, завершённых в течение 12 недель, от числа инициатив, включённых в первоначальный план. Инициативы, в которых есть отменённые или не взятые в квартал задачи, исключаются из знаменателя.

**Sprint Say/Do Ratio** — отношение фактически завершённых Story Points к Story Points из исходного baseline-плана конкретного спринта. Считается по полностью завершённым задачам. Если в спринте не было commit SP, показатель не рассчитывается.

**Bus Factor** — число уникальных владельцев навыка. Целевое значение больше 1 для всех критических технологий.

## Управление данными

Интерфейс позволяет изменять исходные данные без редактирования Excel.

- Инженеры: добавление, редактирование, перевод в статусы Больничный / Отпуск / Уволен с указанием дат. Массовые действия по выбранным инженерам. Полное удаление с сохранением записи в журнале.
- Команды: создание, переименование, удаление с проверкой ссылок. Ручная настройка SP capacity.
- Задачи: добавление с указанием часов по ролям, стартового спринта, зависимостей. Редактирование и каскадное удаление.
- Зависимости: добавление и удаление связей с проверкой на циклы.
- Сметы: редактирование часов по ролям с автоматической проверкой расхождения с `estimated_hh`.

Все изменения сначала попадают в рабочую копию. В базу они записываются только после нажатия «Сохранить». До этого их можно отменить.

## Хранение и журнал

Состояние хранится в SQLite-файле `state.db` рядом с датасетом. Каждое сохранение создаёт снапшот; к любому снапшоту можно откатиться.

Журнал событий фиксирует:

- входы и смены роли пользователя;
- попытки доступа к защищённым разделам, в том числе отказанные;
- все изменения данных с указанием автора, времени, старого и нового значения.

## Разграничение доступа

Три роли с разными правами:

- `admin` — полный доступ, включая управление пользователями;
- `planner` — планирование и редактирование данных;
- `viewer` — только просмотр плана и звёздной карты.

Пароли захардкожены для демонстрации. Архитектура готова к подключению корпоративного SSO без изменений в остальном коде.

## Допущения

1. Квартал — 6 спринтов по 2 недели, всего 12 недель.
2. Focus Factor равен 0.8.
3. Ставка 1.0 даёт 80 часов на спринт.
4. SP резервируются один раз, при первом включении задачи в план.
5. SP и ЧЧ — независимые величины.
6. Зависимости имеют приоритет над ресурсами: даже при свободных часах задача не начнётся раньше предшественника + 1 спринт.
7. Технологическое соответствие проверяется по ключевым навыкам роли. Донор не может отдать часы, если в его команде нет инженера с подходящим стеком.
8. Больничные, отпуска и увольнения учитываются по точным датам, а не «по всему кварталу».
9. Задачи с дублирующимся `task_id` исключаются из планирования.
10. Статусы «Отменено заказ» и «Не будет взято в квартал» исключают задачу из плана и из знаменателя PI Predictability.
11. Ручной override SP capacity полностью перекрывает расчёт из истории.
12. Инженеры с `capacity_rate < 1.0` суммируются по обеим командам, их время жёстко ограничено.

## Известные ограничения

1. Задача с `estimation_sp` больше ёмкости команды на спринт не будет запланирована никогда. Лечится либо ручным override SP capacity, либо снижением оценки задачи.
2. SP capacity не масштабируется автоматически при изменении состава команды. При найме или увольнении нужно задать override вручную.
3. При запрете перевода донор ищется заново, но информация об этом не выделена в интерфейсе отдельно.
4. Экспорт возможен только в CSV. Экспорт в Excel с сохранением структуры не реализован.
5. Встроенной системы добавления задач через UI достаточно для базовых сценариев, но массовый импорт из внешних систем отсутствует.
