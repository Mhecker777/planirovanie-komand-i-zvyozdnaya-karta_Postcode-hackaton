# Команда Без Даты
# ПочтаТех — Квартальное планирование и звёздная карта компетенций

Сервис автоматизирует квартальное PI-планирование для нескольких инженерных команд и одновременно показывает распределение компетенций и риски, связанные с уникальными носителями навыков.

Проект состоит из двух обязательных частей:

- планировщик, который распределяет задачи по 6 двухнедельным спринтам с учётом Story Points, человеко-часов, зависимостей и доступности специалистов;
- звёздная карта, которая считает Bus Factor по компетенциям и показывает, какие навыки держатся на одном человеке.

---

## Требования

- Windows 10 или 11
- **Python 3.10, 3.11, 3.12 или 3.13** — рекомендуется 3.12 или 3.13

```

Если команда не найдена или версия ниже 3.10 — переустановить Python с [python.org](https://www.python.org/downloads/).

## Запуск

### Способ 1. Через `.bat` (рекомендуется)

1. Скопировать папку проекта на локальный диск (не запускать из сетевой папки или из `Program Files`).
2. Положить файл `dataset.xlsx` в одну из папок: `data/`, корень проекта или `src/data/`.
3. Запустить `Planirovanie.bat` двойным кликом.

Скрипт сам проверит Python, создаст виртуальное окружение `.venv`, поставит зависимости из `requirements.txt` и откроет приложение в браузере. Первый запуск занимает 1–3 минуты, повторные — несколько секунд.

### Способ 2. Вручную из PowerShell (с venv)

Открыть PowerShell и выполнить:

```powershell
cd C:\путь\к\проекту
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run src\app.py
```

`cd` — переход в папку проекта. `venv` создаётся один раз, при повторных запусках его создавать не нужно.

Запустить приложение (после того как venv уже создан):

```powershell
cd C:\путь\к\проекту
.\.venv\Scripts\python.exe -m streamlit run src\app.py
```

### Способ 3. Вручную без venv, глобальным Python

Если не хотите возиться с виртуальным окружением и готовы поставить пакеты в системный Python:

```powershell
cd C:\путь\к\проекту
python -m pip install -r requirements.txt
python -m streamlit run src\app.py
```

Здесь `python` — это глобальный Python из PATH, версии 3.10–3.13. Все пакеты установятся в него. Такой способ проще, но менее изолирован: если позже обновить или сломать какой-то пакет в глобальном Python, это затронет и другие проекты.

### Как остановить

`Ctrl+C` в окне терминала (или в окне `.bat`). Окно закроется, приложение остановится.

## Входные данные

Проект работает с одним Excel-файлом, который содержит 5 секций подряд на одном листе.

**Tasks** — список задач. Используются поля: `task_id`, `parent_id`, `summary`, `team_id`, `status`, `rung`, `estimation_sp`, `estimated_hh`, `Номер инициативы`, плановые и фактические даты.

**Estimates** — матрица трудозатрат. Строки — роли, столбцы — `task_id`, значения — человеко-часы.

**Task_dependencies** — направленный граф зависимостей: `blocking_task_id`, `blocked_task_id`, `dependency_type`.

**Engineers_profiles** — инженеры: `engineer_id`, `team_id`, `role`, `grade`, `skills_declared`, `capacity_rate`.

**Team_history** — история производительности: `snapshot_date`, `team_id`, `velocity_achieved`, `planned_sp`.

Парсер читает файл как единую сетку без заголовков и вырезает секции по маркерам шапок. Имена колонок в шапке не используются, только позиции — это устойчиво к сдвигам.

## Алгоритм планирования

### Ёмкость команды в Story Points

Номинальная ёмкость команды на спринт рассчитывается по истории:

```
доступная ёмкость = средний velocity_achieved × 0.8
```

Коэффициент 0.8 — Focus Factor, учитывает техдолг, баги и созвоны. Значения velocity берутся из `Team_history`, некорректные и отрицательные строки игнорируются. Если для команды задан ручной override SP capacity через интерфейс, он используется вместо расчёта из истории.

### Фонд человеко-часов по ролям

```
hours_per_sprint = capacity_rate × 80
```

Ставка 1.0 даёт 80 часов за 2-недельный спринт, ставка 0.5 — 40 часов. Часы суммируются по связке «команда + роль» **отдельно для каждого из 6 спринтов**.

Больничные и отпуска учитываются поспринтово: если период отсутствия инженера пересекается со спринтом, инженер исключается только из этого спринта. Если даты отсутствия не заданы, инженер исключается из всего квартала. Уволенные исключаются полностью.

### Приоритет задач

Задачи сортируются лексикографически:

```
(active, -rung, init_size, task_id)
```

- `active` — 0 для задач в статусе InProgress, 1 для остальных. Начатые задачи получают приоритет.
- `-rung` — больший rung раньше.
- `init_size` — суммарный SP инициативы, меньшие инициативы раньше.
- `task_id` — стабильный tie-breaker.

Порядок внутри графа зависимостей сохраняется: потомок не может быть раньше предшественника.

### Зависимости

Между блокирующей и блокируемой задачей выдерживается минимум один спринт зазора. Реализовано условием `sprint_when_done[predecessor] < current_sprint`. Циклы зависимостей обнаруживаются через NetworkX, задачи цикла исключаются из автоматического планирования.

### Двухпроходное распределение

Для каждого спринта создаются свежие пулы SP и ЧЧ.

**Проход 1.** Каждая команда закрывает задачи своими силами. Если часов по всем ролям хватает, задача планируется в этом спринте. Если SP команды меньше требуемого (и SP ещё не были закоммичены), задача переносится на следующий спринт.

**Проход 2.** Для задач, которым не хватило часов, ищутся доноры. Донором может быть другая команда, у которой после первого прохода остались свободные часы нужной роли. Дополнительно проверяется, что в команде-доноре есть хотя бы один инженер с ключевым навыком для этой роли. Часы переводятся жадно, по убыванию доступного объёма. Пользователь может запретить конкретную связку «команда + роль».

### Сплиттинг

Если задачу нельзя выполнить целиком в одном спринте, но часть часов доступна, выполняется доступный объём, остаток переносится в следующий спринт. Story Points резервируются один раз, при первом включении задачи. При повторном включении в следующий спринт SP не списываются.

### Story Points и человеко-часы

SP и ЧЧ — независимые величины.

SP отражают сложность задачи и являются обязательством команды перед заказчиком. Списание SP происходит один раз, при первом включении задачи в план. Если задача растягивается на несколько спринтов, SP не пересчитываются.

ЧЧ отражают конкретную загрузку специалистов по ролям. Именно ЧЧ расходуются из поспринтовых пулов, и именно они определяют, влезает задача в спринт или нет.

Связь между SP и ЧЧ в алгоритме отсутствует: это две отдельные шкалы, которые используются параллельно.

## Настройки планирования: режим работы с 1С-ролями

В датасете нет ни одного инженера 1С-направления (`Аналитик 1С`, `Разработчик 1С`, `Архитектор 1С`, `Специалист поддержки 1С`). При этом в смете нескольких задач эти роли присутствуют. Возникает выбор: игнорировать эти часы и планировать задачу по остальным ролям, или считать задачу невыполнимой целиком. Оба варианта — легитимны с точки зрения бизнес-логики, и выбор зависит от политики заказчика.

В сайдбаре есть переключатель **«Игнорировать 1С-роли при планировании»**:

| Режим | Поведение |
|---|---|
| **Включён** (по умолчанию) | 1С-роли в смете игнорируются. Задача планируется по остальным ролям. Часы по 1С-ролям не списываются из фонда и не учитываются при расчёте. Задача может получить статус «Завершена», хотя фактически 1С-часть не выполнена. |
| **Выключен** | Задача с любой 1С-ролью в смете **снимается с плана целиком**. Она не попадает ни в один спринт, и отображается в разделе «План и Задачи → Статус незавершённых задач → Не поместились в квартал» с категорией **«Нет специалистов 1С»** и причиной вида «Нет специалистов 1С: Аналитик 1С». |

### Смена режима требует подтверждения

Клик по чекбоксу **не пересчитывает план мгновенно** — смена режима может перекроить весь график, поэтому система требует явного подтверждения:

1. Пользователь кликает по чекбоксу.
2. В сайдбаре появляется предупреждение: «Сейчас: … Станет: … План будет пересчитан только после подтверждения».
3. Две кнопки: **«✅ Подтвердить»** (фиксирует новый режим и запускает пересчёт) и **«↩️ Отмена»** (возвращает чекбокс к прежнему значению без пересчёта).
4. До подтверждения планировщик использует **прежнее** значение — случайный клик не перекроит план.

### Настройка сохраняется между сессиями

Режим 1С хранится в SQLite-таблице `runtime_state` вместе с симуляцией времени, фактом и датой старта квартала. Перезапуск приложения, обновление страницы (F5) или повторное открытие — состояние восстанавливается автоматически. Это отличает его от эфемерного `st.session_state`: то, что раньше сбрасывалось при перезагрузке, теперь живёт в базе.

## Пересчёт по факту

Раз в две недели пользователь отмечает задачи, реально завершённые в спринте. По умолчанию в интерфейсе отмечены все задачи, запланированные к завершению — снимаются галочки с тех, что фактически не закрылись.

После внесения факта планировщик:

- принимает отмеченные задачи как завершённые и фиксирует списание часов по факту;
- для незакрытых задач из baseline показывает статус «Не выполнена (Факт)»;
- для сплитованных задач переносит остаток часов без повторного списания SP;
- пересчитывает оставшуюся часть квартала.

Отклонения вызывают алерты:

- красный — задача не завершена за 6 спринтов, инициатива под угрозой;
- жёлтый — задержка задачи реально блокировала потомков по графу зависимостей;
- оранжевый — ресурсный дефицит по роли в конкретном спринте, либо перерасход факта относительно фонда;
- коричневый — структурный дефицит: роли нет в штате команды или во всей компании;
- фиолетовый — парттайм: инженер с неполной ставкой ограничивает суммарный ресурс команды.

**Отдельно про 1С:** при выключенном режиме «Игнорировать 1С-роли» задачи с 1С-ролями снимаются с плана и не порождают отдельного алерта — информация видна через раздел «Не поместились в квартал» с причиной `no_1c_specialist`. Это сознательное решение: задача не «частично не выполнена», а «не может быть выполнена вообще», и её место — в списке исключённых, а не в алертах о ходе квартала.

## Звёздная карта и Bus Factor

Для каждого навыка считается Bus Factor — сколько разных инженеров им владеют. Навык с Bus Factor = 1 считается критичным.

Для критичных навыков подбираются кандидаты на дообучение по принципу TF-IDF: вес навыка обратно пропорционален числу его носителей, поэтому редкие навыки дают больший вес при подборе кандидата. Если кандидат сам является единственным носителем какого-либо навыка, его оценка умножается на 0.5, чтобы не создавать новое узкое место.

Дополнительно считается Bus Factor в разрезе отдельных команд. Навык может быть не критичным для компании в целом, но критичным для конкретной команды — тогда именно эта команда остановится при уходе носителя.

В интерфейсе отображаются:

- KPI по доле критичных навыков;
- тепловая карта «навык × команда» — сколько инженеров в каждой команде владеют каждым навыком;
- полная таблица Bus Factor по компании и по командам;
- связка критичных навыков с конкретными задачами квартала.

Уволенные инженеры исключаются из расчёта Bus Factor сразу после перевода в соответствующий статус.

## Показатели эффективности

**PI Predictability Measure** — доля инициатив, завершённых в течение 12 недель, от числа инициатив, включённых в первоначальный план. Инициативы, в которых есть отменённые или не взятые в квартал задачи, исключаются из знаменателя.

**Sprint Say/Do Ratio** — отношение фактически завершённых Story Points к Story Points из исходного baseline-плана конкретного спринта. Считается по полностью завершённым задачам. Если в спринте не было commit SP, показатель не рассчитывается.

**Bus Factor** — число уникальных владельцев навыка. Целевое значение больше 1 для всех критических технологий.

## Управление данными

Интерфейс позволяет изменять исходные данные без редактирования Excel.

- Инженеры: добавление, редактирование, перевод в статусы Больничный / Отпуск / Уволен с указанием дат. Массовые действия по выбранным инженерам. Полное удаление с сохранением записи в журнале.
- Команды: создание, переименование, удаление с проверкой ссылок. Ручная настройка SP capacity.
- Задачи: добавление с указанием часов по ролям, стартового спринта, зависимостей. Редактирование и каскадное удаление.
- Зависимости: добавление и удаление связей с проверкой на циклы.
- Сметы: редактирование часов по ролям с автоматической проверкой расхождения с `estimated_hh`.

Все изменения сначала попадают в рабочую копию. В базу они записываются только после нажатия «Сохранить». До этого их можно отменить.

## Хранение и журнал

Состояние хранится в SQLite-файле `state.db` рядом с датасетом. Каждое сохранение создаёт снапшот; к любому снапшоту можно откатиться.

Журнал событий фиксирует:

- входы и смены роли пользователя;
- попытки доступа к защищённым разделам, в том числе отказанные;
- все изменения данных с указанием автора, времени, старого и нового значения.

## Разграничение доступа

**Текущий статус: аутентификация работает, разграничение прав — нет.**

В сайдбаре есть панель «Аккаунт» с выбором пользователя и вводом пароля. Войти можно под одной из трёх учётных записей:

| Пользователь | Пароль | Права по ролям |
|---|---|---|
| `admin` | `admin` | полный доступ |
| `planner` | `planner` | планирование и редактирование данных |
| `viewer` | `Viewr` | только просмотр |

При успешном входе запись о смене роли попадает в журнал событий.

**Почему разграничение прав не работает в полном объёме.** Форма входа — это демонстрационный слой. В `auth.py` описаны три роли и матрица прав (`edit_data`, `view_audit`, `manage_users`), функция `require_permission` умеет проверять права и логировать отказы. Но текущая реализация не является настоящей системой безопасности:

- **пароли хранятся в открытом виде** прямо в коде `auth.py`;
- **нет хеширования** (bcrypt / argon2), нет срока жизни сессии, нет блокировки после неудачных попыток;
- **role switching не блокирует интерфейс** — любой пользователь, знающий пароль `admin`, может переключиться на администратора из сайдбара.

Для боевого использования нужны: хеширование паролей, вынос учётных записей в отдельное хранилище, управление пользователями через UI, замена `try_login` на обмен токеном с корпоративным SSO/OAuth-провайдером. Архитектурно код к этому готов — достаточно подменить реализацию `try_login`, не переписывая проверки в `app.py` и `data_management.py`.

Функция `require_permission` сознательно **не вызывает `st.stop()`** — иначе отказ в одной вкладке ломает рендер соседних вкладок в том же прогоне Streamlit. По умолчанию она возвращает `False`, показывает сообщение и передаёт решение вызывающему коду. Параметр `stop_on_denied=True` оставлен для сценариев, где жёсткий стоп действительно нужен.

**Переключение ролей не доведено до продакшн-уровня.** Это осознанный компромисс демо-слоя: показать архитектуру разграничения доступа без построения полноценной системы безопасности. В проде этот слой заменяется на корпоративный SSO/OAuth — достаточно подменить реализацию `try_login`, вся остальная логика проверок (`has_permission`, `require_permission`, журналирование отказов) остаётся без изменений.

## Допущения

1. Квартал — 6 спринтов по 2 недели, всего 12 недель.
2. Focus Factor равен 0.8.
3. Ставка 1.0 даёт 80 часов на спринт.
4. SP резервируются один раз, при первом включении задачи в план.
5. SP и ЧЧ — независимые величины.
6. Зависимости имеют приоритет над ресурсами: даже при свободных часах задача не начнётся раньше предшественника + 1 спринт.
7. Технологическое соответствие проверяется по ключевым навыкам роли. Донор не может отдать часы, если в его команде нет инженера с подходящим стеком.
8. Больничные, отпуска и увольнения учитываются по точным датам, а не «по всему кварталу».
9. Задачи с дублирующимся `task_id` исключаются из планирования.
10. Статусы «Отменено заказ» и «Не будет взято в квартал» исключают задачу из плана и из знаменателя PI Predictability.
11. Ручной override SP capacity полностью перекрывает расчёт из истории.
12. Инженеры с `capacity_rate < 1.0` суммируются по обеим командам, их время жёстко ограничено.
13. Задачи с 1С-ролями в смете при выключенном режиме «Игнорировать 1С-роли» снимаются с плана целиком. При включённом режиме (по умолчанию) они планируются по остальным ролям, а 1С-часы не учитываются.
14. Выбор режима 1С сохраняется в SQLite и переживает перезапуск приложения и F5.
15. Смена режима 1С требует явного подтверждения — до нажатия «Подтвердить» план считается по прежнему режиму.

## Пересчёт при любом изменении данных

Планировщик и звёздная карта пересчитываются **на каждом rerun Streamlit** — то есть мгновенно реагируют на любые действия в интерфейсе:

- перевод инженера в **больничный / отпуск / уволен** — часы немедленно исчезают из поспринтовых пулов тех спринтов, которые пересекаются с периодом отсутствия;
- **возврат в работу** — часы появляются обратно во все спринты квартала;
- **массовые действия** по выбранным инженерам — пересчёт по всем затронутым командам и ролям сразу;
- **добавление новой задачи** через UI — попадает в план со следующего спринта после текущего;
- **редактирование сметы** — пересчитываются все зависимые от неё задачи;
- **добавление/удаление зависимостей** — пересчёт топологического порядка и проверка на циклы;
- **ручной override SP capacity** для команды — все задачи этой команды пересчитываются с новой ёмкостью;
- **запрет донора** через сайдбар — планировщик ищет нового донора или показывает дефицит;
- **переключение режима 1С-ролей** — после подтверждения задачи с 1С-ролями либо возвращаются в план, либо снимаются с него; план пересчитывается целиком;
- **внесение факта по спринту** — пересчёт оставшейся части квартала, обновление Say/Do, обновление PI Predictability.

Все правки в «Управление данными» работают по модели **working copy**: изменения видны только в текущей сессии, пока пользователь не нажмёт «Сохранить». Кнопка «Отменить все правки» откатывает рабочую копию к последнему снапшоту.

## Новые задачи не попадают в прошедшие спринты

При добавлении задачи через UI поле **«Стартовый спринт»** по умолчанию выставляется в `текущий_спринт + 1`. Если пользователь завершил Спринт 3 и добавляет задачу — она автоматически ставится с 4-го спринта. Планировщик проверяет `sprint < task_start_sprint` и молча пропускает задачу в более ранних спринтах — она физически не может быть втиснута в уже завершённый период.

Значение `start_sprint` хранится в `tasks_df` и редактируется в таблице задач. Колонка `start_sprint` отсутствует в исходном Excel — она добавляется планировщиком со значением 1 по умолчанию, так что существующие задачи не меняют поведение.

## Скрытый функционал, важный для понимания системы

Ниже — возможности, которые не лежат на поверхности, но сильно влияют на качество планирования и на то, как система ведёт себя в граничных сценариях.

### Планировщик

- **Двухпроходный жадный алгоритм.** Сначала каждая команда пытается закрыть задачу своими силами. Только если своих часов не хватает, включается поиск доноров. Это исключает ситуации, когда задача получает перевод от другой команды, хотя своя команда могла её выполнить.

- **Подбор конкретного инженера-донора.** Функция `_pick_donor_engineer` выбирает не «команду вообще», а конкретного человека: только активные (не уволен, не на больничном/отпуске), максимальная ставка, при равенстве — лексикографически первый ID. Результат попадает в лог переводов как `donor_engineer`.

- **Проверка технологического соответствия донора.** Донор не может отдать часы по роли, если в его команде нет ни одного инженера с подходящим навыком. Проверка идёт по словарю `role_required_skills` — например, для роли «Разработчик Java» нужен инженер с `java` в `skills_declared`. При этом проверка ищет ключевое слово как подстроку (не точное совпадение), поэтому «agile/scrum» подходит под ключ `agile`.

- **Запрет конкретных переводов.** Пользователь в сайдбаре может пометить связку «донор + роль» как запрещённую. Планировщик ищет следующего донора, а если не находит — задача переносится с кодом `role_capacity`.

- **Свежие пулы SP и ЧЧ на каждый спринт.** Задачи, перенесённые из спринта N в N+1, не «съедают» SP дважды: резервирование отслеживается через `reserved_sp`. Часы при этом расходуются честно — из пула нового спринта.

- **Поспринтовый учёт отсутствий.** Инженер с больничным 10–20 число выпадает только из того спринта, чей диапазон дат пересекается с этим периодом. В остальных спринтах квартала его часы доступны.

- **Разделение сметы на «все роли» и «роли в штате».** `task_estimates` содержит только роли, для которых есть сотрудники; `task_estimates_raw` — все роли из Excel. Это позволяет отдельно алертить «роль отсутствует в компании» (структурный дефицит) и «роль есть, но специалист недоступен» (нет доступного специалиста).

- **Логика `InProgress` сохраняется через пересчёт.** Если задача была растянута в факте или провалена как «Не выполнена (Факт)», она переводится в статус `InProgress` и при пересчёте получает приоритет в топологической сортировке.
