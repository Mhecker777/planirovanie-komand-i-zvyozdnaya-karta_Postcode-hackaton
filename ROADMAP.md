# План развития сервиса квартального планирования и «Звёздной карты» — ПочтаТех

*Обновлено после проверки рабочей версии на реальном `dataset.xlsx` (парсер под Excel, авто-реорганизация команд, «машина времени» факта, рекомендации по дообучению — уже реализованы и протестированы).*

---

## 0. Текущее состояние (зафиксировано проверкой)

Уже реализовано и подтверждено рабочим прогоном на 45 задачах / 34 инженерах / 16 связях:
- Парсер читает Excel позиционно, без сдвигов колонок (16/16 зависимостей читаются верно).
- Зазор в 1 спринт между зависимыми задачами соблюдается через топологическую сортировку + `sprint_when_done`.
- Автоматическая реорганизация (перевод часов между командами) — работает, логируется отдельным действием `Реорганизация (Перевод)`.
- «Машина времени»: ввод факта по прошедшим спринтам через сайдбар, пересчёт хвоста плана.
- Трекер утилизации сотрудников (вкладка 2).
- Bus Factor + базовые рекомендации по дообучению (вкладка 4).
- 3 типа алертов (🔴🟡🟠).

**Найдено при проверке — требует исправления до сдачи:**
1. `Sprint 1 Say/Do Ratio` — считается из одного и того же пересчитанного плана (числитель и знаменатель совпадают по построению), метрика не может показать ничего, кроме ~100%, даже при полном провале спринта (проверено на смоделированном провале).
2. Рекомендации «кого дообучить» — пересечение навыков сейчас считается «в лоб», без веса; общие непрофильные навыки (REST API, SQL, Git, Postman) создают нерелевантные рекомендации (пример: QA-инженера рекомендуют дообучить на Android-разработчика из-за общего навыка «Java»).
3. `заказчик`/`исполнитель`/`плановый результат` — подтверждено, что это не баг парсинга, а проблема в самих исходных данных (одинаковый служебный текст почти во всех строках). Нужно решение: чистить/игнорировать эти поля или уточнить у составителей.
4. SP-бюджет команды-донора не уменьшается при передаче ею часов другой команде — не баг, но нужно явно задокументировать как допущение.

## 1. Этап 0 — Довести до сдачи (первоочередное)

### 1.1 Исправить Say/Do Ratio
- Считать `Sprint N Say/Do` как `SP факта / SP из ПЕРВОНАЧАЛЬНОГО baseline-плана` (тот, что уже есть в `app.py` как `b_schedule`, просто сейчас не используется для этой метрики) — не пересчитывать знаменатель заново из скорректированного плана.
- Технически: передавать `b_kpis`/`b_schedule[N]` явно в функцию расчёта KPI при пересчёте, а не только `c_schedule`.
- Добавить эту же логику для **всех** прошедших спринтов, а не только для первого (сейчас формула в коде жёстко привязана к `sprint_schedule[1]`).

### 1.2 Доработать логику рекомендаций по дообучению
- Ввести вес значимости навыка: чем реже навык встречается в компании, тем выше вес совпадения (аналог TF-IDF: редкий совместно встречающийся навык — сильный сигнал, «SQL» или «Git» — слабый).
- Альтернативный/дополняющий вариант проще в реализации: явно сгруппировать навыки по экосистемам (мобильная разработка, фронтенд, бэкенд Java/.NET, BigData, DevOps, QA-автоматизация) и в первую очередь предлагать кандидатов из той же экосистемы, а не по сырому пересечению.
- Показывать в интерфейсе не только «общих навыков: N», но и **какие именно** навыки совпали — сейчас это скрыто, а по нему сразу видно, релевантна рекомендация или нет.

### 1.3 Зафиксировать допущения в README
- SP-бюджет донора не снижается при передаче часов (п.4 выше).
- `заказчик`/`исполнитель`/`плановый результат` не используются как надёжный источник (п.3 выше) — либо, если получится уточнить у составителей, описать корректную интерпретацию.
- Роли без сотрудников в штате (1С-роли, «Специалист поддержки», «Руководитель проекта») по-прежнему не блокируют план — те же основания, что обсуждали раньше.
- Округление ёмкости команды — вниз.
- Порядок приоритизации: `InProgress` → сначала более мелкие по SP инициативы → затем более высокий `rung` (объяснить именно эту логику — почему сначала мелкие инициативы, это осознанный выбор ради `PI Predictability`, а не просто побочный эффект).

### 1.4 Мелкие технические доводки
- Использовать уже читаемые, но пока не применяемые в планировании поля: `planned_start/end`, `actual_start/end`, `spent_time`, `estimated_hh` (как проверка целостности сметы — сверить с суммой по ролям и вывести предупреждение при расхождении), `parent_id` (группировка в UI).
- Проверить, не «голодает» ли команда-донор сама из-за порядка перебора при автопереводе часов (сейчас перебор доноров идёт в порядке появления команд в Excel, а не по признаку «у кого точно есть излишек в этом спринте») — минимальный фикс: при выборе донора предпочитать команду, у которой после передачи всё ещё останется резерв под её собственные задачи этого спринта (посчитать наперёд её собственную потребность).

## 2. Этап 1 — Довести полноту продукта под требования ТЗ и обсуждённую бизнес-логику

### 2.1 Явное разведение «автоматической» и «управляемой» реорганизации
Сейчас перевод часов между командами происходит полностью автоматически и незаметно для пользователя на каждый чих (89 переводов за квартал). Это хорошо для честного плана, но плохо для управляемости — реальный тимлид должен видеть и по возможности согласовывать это, а не узнавать постфактум из лога.
- Добавить экран **«Реорганизации этого прогона»** — сводка (не построчный лог, а агрегат): какая команда сколько часов какой роли отдала/получила за квартал, чтобы сразу было видно масштаб зависимости команд друг от друга.
- Дать пользователю возможность **запретить** конкретный перевод (например, «Team-L не должна отдавать Java-часы, у них у самих запара») и пересчитать план с этим ограничением — это уже реальный рычаг управления, а не просто наблюдение.

### 2.2 Bus Factor в разрезе команд (сейчас только общий по компании)
- Добавить агрегацию `get_bus_factor_and_training()` с группировкой по `team_id`: для каждой команды отдельно — какие навыки внутри именно неё держатся на одном человеке.
- Вывести как drill-down на вкладке «Звёздная карта»: сводная таблица по компании → клик по команде → детализация.

### 2.3 Улучшить обоснованность алертов
- 🟡 каскадный алерт сейчас срабатывает для любой `InProgress`-задачи с зависимыми — независимо от того, реально ли под угрозой финальный дедлайн. Уточнить: считать каскадный риск только если сдвиг данной задачи может вывести хотя бы одного потомка за пределы 12 недель (посчитать вперёд минимально необходимое число спринтов для цепочки).
- 🟠 ресурсный дефицит — сейчас один агрегированный алерт на роль по всему остатку бэклога. Разбить по спринтам («на следующий спринт не хватит N ЧЧ роли Х»), это ближе к формулировке ТЗ («риски... на следующий спринт»).

### 2.4 Честная историческая точность команды
Использовать теперь читаемое поле `planned_sp` из `Team_history` (сейчас парсится, но не используется) — сравнить с `velocity_achieved` по каждому историческому спринту и считать не только среднюю скорость, но и **стабильность** (разброс/стандартное отклонение) — команда с тем же средним, но стабильным исполнением надёжнее для планирования, чем команда с тем же средним, но большим разбросом. Можно показывать это как дополнительный, более честный сигнал доверия к плану.

## 3. Этап 2 — UX и презентация

- Крупный, разборчивый интерфейс — крупные метрики, карточки риска вместо только табличных списков.
- Экран сравнения plan vs факт по прошедшим спринтам (не только цифра Say/Do, но и визуально — что было запланировано и что реально сделано).
- Понятная легенда терминов на первом экране: Bus Factor, Растянута, Реорганизация, зазор зависимостей.
- В рекомендациях по дообучению — показывать совпавшие навыки явно (после фикса 1.2), чтобы рекомендация была проверяемой глазами, а не «чёрным ящиком».
- Фильтры на вкладке логов — по команде и по инициативе, не только по действию и `task_id`.

## 4. Этап 3 — Продакшн-уровень для реального использования в ПочтаТех

- **Полноценное управление задачами**: CRUD задач/инициатив, ручная смена статуса вне цикла пересчёта, история изменений, комментарии.
- **Синхронизация с календарём**: перейти от номеров спринтов к реальным датам, используя уже читаемые `planned_start/end`/`actual_start/end` — автоопределение текущего спринта по сегодняшней дате вместо ручного слайдера «машины времени».
- **Формализованный workflow реорганизации**: перевод конкретного инженера между командами как согласуемое действие с датой начала/окончания и историей — развитие пункта 2.1.
- **Распределение по конкретным инженерам**, а не только по агрегированным часам роли — чтобы не «занимать» одного и того же человека дважды в модели.
- Аутентификация и роли доступа, интеграции с Jira/Azure DevOps вместо ручной выгрузки в Excel, экспорт отчётов, версионирование планов и трендов KPI по кварталам.

## 5. Этап 4 — Идеи на будущее (видение продукта)

- Полноценный **рекомендательный движок по реорганизации**: система сама предлагает минимальный набор переводов, а не проводит их все автоматически без разбора (развитие 2.1).
- ML-скоринг близости навыков для дообучения — развитие 1.2 с учётом совместной встречаемости технологий в реальных проектах компании, а не только формального списка.
- What-if сценарии найма.
- Интеграция с корпоративным мессенджером, мобильная версия.
