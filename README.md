# 📦 ПочтаТех — Квартальное планирование и Звёздная карта компетенций

Сервис для автоматизации квартального PI-планирования и анализа компетенций инженеров.

Решает две задачи:

1. **Квартальное планирование** — распределение задач по 6 двухнедельным спринтам
   с учётом Story Points, трудозатрат по ролям, зависимостей и фактических результатов.
2. **Звёздная карта** — профили инженеров, команд, расчёт Bus Factor и поиск
   критических компетенций.

---

### Требования

## 🧩 Архитектура

### 1. `parser.py` — DataParser

Читает Excel как единую сетку (`header=None`) и вырезает секции по маркерам шапок:

| Метод | Секция | Маркер |
|---|---|---|
| `get_tasks()` | Tasks | `Номер инициативы` |
| `get_estimates()` | Estimates | `Роль` |
| `get_dependencies()` | Task_dependencies | `blocking_task_id` |
| `get_engineers()` | Engineers_profiles | `engineer_id` |
| `get_team_history()` | Team_history | `snapshot_date` |

Парсер режет таблицы строго по позиции столбцов, а не по именам — это устойчиво к
сдвигам шапки в исходном Excel.

### 2. `scheduler.py` — SmartScheduler

Ядро планирования. Основные шаги:

1. Валидация и нормализация задач, зависимостей, инженеров, истории.
2. Построение графа зависимостей (NetworkX DiGraph).
3. Расчёт SP-ёмкости команд и фонда часов по ролям.
4. Топологическая сортировка задач с приоритетами.
5. Итеративное планирование по 6 спринтам с учётом SP, ЧЧ, зависимостей,
   переводов между командами и технологического соответствия.
6. Формирование алертов и KPI.

### 3. `analytics.py` — StarMapAnalytics

- `get_bus_factor_and_training()` — Bus Factor по компании + рекомендации по дообучению.
- `get_bus_factor_by_team()` — Bus Factor в разрезе команд.
- `get_critical_roles_shortage()` — роли с одним сотрудником в команде.
- `get_critical_skill_tasks()` — связка критичных навыков с задачами.
- `get_star_map_data()` — данные для визуализации звёздной карты.

### 4. `app.py` — Streamlit UI

Пять вкладок:

1. **📅 План и Задачи** — Gantt (`px.timeline`), список невыполненных задач с причинами.
2. **👥 Трекер сотрудников** — утилизация, историческая стабильность команд.
3. **💡 Лог решений** — фильтруемый журнал действий планировщика.
4. **⭐ Звёздная карта** — Bus Factor по компании и командам.
5. **⚠️ Алерты** — красные / жёлтые / оранжевые / фиолетовые / коричневые.

Боковая панель: выбор старта квартала, симуляция времени, ввод факта,
управление реорганизацией.

## ⚙️ Алгоритмы

### Ёмкость команды в Story Points

```
Доступная ёмкость (SP/спринт) = средний velocity_achieved × 0.8
```

- `0.8` — Focus Factor (20% на техдолг, баги, созвоны).
- `velocity_achieved` берётся из `Team_history` по каждой команде.
- Некорректные и отрицательные значения игнорируются.

### Фонд человеко-часов по ролям

```
hours_per_sprint = capacity_rate × 80
```

- `capacity_rate = 1.0` → 80 ЧЧ/спринт.
- `capacity_rate = 0.5` → 40 ЧЧ/спринт.
- Часы суммируются по связке «команда + роль».

### Приоритет задач (скоринг)

Задачи сортируются лексикографически:

```
(active, размер_инициативы, -rung, task_id)
```

- `active = 0` для InProgress (приоритет выше).
- `размер_инициативы` — сумма SP по всем задачам инициативы (меньше — раньше).
- `-rung` — больший `rung` раньше.
- `task_id` — стабильный tie-breaker.

### Зависимости

- Между блокирующей и блокируемой задачей — минимум 1 спринт зазора.
- Реализовано как `sprint_when_done[predecessor] < current_sprint`.
- Циклы зависимостей детектируются через `nx.simple_cycles`, задачи цикла
  исключаются из автоматического планирования.

### Технологическое соответствие

Для каждой роли задан набор ключевых навыков (`role_required_skills`).
Перевод часов от команды-донора разрешён только если в команде-доноре есть
хотя бы один инженер с ключевым навыком для этой роли. Если ни в одной команде
нет нужного навыка — задача получает алерт `🟤 СТРУКТУРНЫЙ ДЕФИЦИТ (НАВЫКИ)`.

### Сплиттинг (растягивание)

Если задачу нельзя выполнить целиком в одном спринте, но часть часов доступна:

- доступный объём списывается в текущем спринте;
- остаток переносится в следующий;
- SP резервируются один раз, при первом включении.

### Реорганизация (Перевод)

Если в команде не хватает часов нужной роли, планировщик ищет доноров среди
других команд с положительным остатком по этой роли. Часы переводятся
жадно, по убыванию доступного объёма. Пользователь может запретить конкретную
связку «донор + роль».

### Факт и пересчёт

Пользователь отмечает реально завершённые задачи по спринтам. Планировщик:

- принимает факт как истину, не пересчитывает завершённые задачи;
- фиксирует перерасход SP/ЧЧ как `🔴 ОШИБКА ФАКТА`;
- для незакрытых задач из baseline показывает статус «Не выполнена (Факт)»;
- пересчитывает только оставшуюся часть квартала.

## 📊 KPI

| KPI | Формула |
|---|---|
| **PI Predictability Measure** | Завершено инициатив / Запланировано инициатив × 100% |
| **Sprint Say/Do Ratio** | Факт SP / Baseline SP × 100% |
| **Bus Factor** | Число уникальных владельцев навыка |

Инициативы с задачами в статусах `Отменено заказ` и `Не будет взято в квартал`
исключаются из знаменателя PI Predictability.

Say/Do считается по **baseline-спринту**, где задача получила commit SP.
Если в спринте нет commit'ов — показывается «н/д (нет commit)».

## 🗂️ Обработка статусов

| Статус в датасете | Внутренний статус | Поведение |
|---|---|---|
| `Done`, `Завершена` | `Done` | Не планируется, учитывается в KPI |
| `InProgress`, `В работе` | `InProgress` | Планируется с повышенным приоритетом |
| `ToDo`, `Planned`, `Новая`, пусто | `Planned` | Планируется стандартно |
| `Отменено заказ`, `Отменено` | `Canceled` | Исключается из плана и алертов |
| `Не будет взято в квартал` | `NotTaken` | Исключается из плана и алертов |
| Неизвестный | `Planned` | Предупреждение в Data Quality |

## ⚠️ Алерты

| Тип | Когда возникает |
|---|---|
| 🔴 **КРИТИЧЕСКИЙ (Срыв инициативы)** | Задача не завершена за 6 спринтов |
| 🔴 **ОШИБКА ФАКТА** | Факт превышает доступный SP или ЧЧ |
| 🔴 **ОШИБКА ПЛАНИРОВАНИЯ** | Превышен лимит SP команды |
| 🟡 **РИСК КАСКАДНОГО СДВИГА** | Задержка задачи реально блокировала потомков |
| 🟠 **РЕСУРСНЫЙ ДЕФИЦИТ** | Не хватило ЧЧ роли даже после переводов |
| 🟣 **ВНИМАНИЕ (Парттайм)** | Инженеры с `capacity_rate < 1.0` |
| 🟤 **СТРУКТУРНЫЙ ДЕФИЦИТ** | Роль отсутствует в команде |
| 🟤 **СТРУКТУРНЫЙ ДЕФИЦИТ (РОЛЬ)** | Роль отсутствует в компании |
| 🟤 **СТРУКТУРНЫЙ ДЕФИЦИТ (НАВЫКИ)** | Ни у одного инженера нет ключевого навыка |

## ⭐ Bus Factor

### Расчёт

```
Bus Factor навыка = число уникальных инженеров, у которых навык в skills_declared
```

Критичный навык — Bus Factor = 1.

### Рекомендации по дообучению

Кандидат подбирается по **взвешенному пересечению навыков** с владельцем:

```
score = Σ (1 / BF(skill)) по всем общим навыкам
```

- Вес обратно пропорционален числу владельцев навыка (аналог IDF).
- Редкие навыки дают больший вес.
- Критичные инженеры получают штраф ×0.5, чтобы не перегружать их.

В рекомендации показываются топ-3 совпавших навыка и команды кандидата.

### Bus Factor по командам

Дополнительно считается Bus Factor в разрезе каждой команды. Навык может быть
не критичным для компании в целом, но критичным для конкретной команды.

## 🧾 Допущения и правила

1. **Квартал = 6 спринтов × 2 недели = 12 недель.**
2. **Focus Factor = 0.8** — 20% времени уходит на техдолг, баги, созвоны.
3. **80 ЧЧ на спринт** при `capacity_rate = 1.0`.
4. **SP резервируются один раз** — при первом включении задачи в план.
5. **SP и ЧЧ — независимые величины.** SP отвечает за commitment команды
   перед заказчиком, ЧЧ — за загрузку конкретных специалистов.
6. **Зависимости имеют приоритет над ресурсами.** Даже при наличии свободных
   часов задача не начнётся раньше, чем завершится предшественник + 1 спринт.
7. **Технологическое соответствие проверяется по ключевым навыкам роли.**
   Если навыка нет ни у кого — задача не может быть выполнена без найма.
8. **Part-time инженеры (`capacity_rate < 1.0`)** суммируются по обеим командам —
   их суммарное доступное время жёстко ограничено.
9. **Отменённые и не взятые в квартал инициативы** исключаются из знаменателя
   PI Predictability Measure.
10. **Неизвестный статус** трактуется как `Planned` с предупреждением.
11. **Задачи с дублирующимися `task_id`** исключаются из планирования.
12. **Циклы зависимостей** исключают задачи цикла из автоматического планирования.
13. **Смета без положительных оценок** по доступным ролям → задача не планируется.
14. **Роль из сметы, которой нет в штате**, игнорируется в планировании часов,
    но фиксируется как структурный дефицит.

## 🎛️ Интерфейс

### Боковая панель

- **Календарь квартала** — дата старта спринта 1.
- **Симуляция времени** — выбор текущего спринта (0–6).
- **Внесение факта** — чекбоксы по задачам каждого пройденного спринта.
  Плюс мультиселект для дополнительно завершённых задач.
- **Управление реорганизацией** — запрет конкретных связок «донор + роль».

### Основные вкладки

- **📅 План и Задачи** — Gantt (timeline), таблица невыполненных задач,
  экспорт CSV.
- **👥 Трекер сотрудников** — утилизация по каждому инженеру, историческая
  стабильность команд, роли с одним сотрудником.
- **💡 Лог решений** — фильтры по действию, команде, инициативе, поиск по `task_id`.
- **⭐ Звёздная карта** — Bus Factor по компании и по командам.
- **⚠️ Алерты** — сгруппированы по типам, с описанием причины.

---

## 🧪 Известные ограничения

1. Планировщик не учитывает пересечение задач по календарю внутри спринта
   (только суммарные часы).
2. Технологическое соответствие проверяется по ключевым навыкам роли,
   а не по конкретному стеку задачи.
3. При переводе часов от донора не проверяется, что донор сам не загружен
   на 100% — используется остаток после уже переведённых часов.
4. Система добавления и управления задачами через UI пока не реализована;
   редактирование возможно только через исходный Excel.
5. Экспорт — только CSV. Excel-экспорт с сохранением структуры не реализован.
6. Дубликаты задач по `task_id` исключаются, а не объединяются.

## 🔧 Расширение

### Добавление новой роли

1. Добавить роль в `Engineers_profiles`.
2. Если у роли есть ключевые навыки — добавить их в `role_required_skills`
   в `scheduler.py`.
3. Добавить столбец в `Estimates` (если роль уже встречается — не нужно).

### Добавление нового типа алерта

1. Добавить запись в `alerts.append({...})` в `scheduler.py` с префиксом
   эмодзи (🔴 / 🟡 / 🟠 / 🟣 / 🟤).
2. Если нужен новый тип — добавить счётчик в `tab5` в `app.py`.
